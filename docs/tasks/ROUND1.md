# Раунд 1 — 20 октября

Логика целиком: [`docs/CONVEYOR.md`](../CONVEYOR.md). Контракты: [`contracts/conveyor.md`](../../contracts/conveyor.md), [`integrations.md`](../../contracts/integrations.md), [`ai.md`](../../contracts/ai.md), [`dictionaries.json`](../../contracts/dictionaries.json), [`rules/credit_rules.v1.json`](../../contracts/rules/credit_rules.v1.json). Проверка контрактов: `cd contracts && npm ci && npm run check`.

## Ветки

- `frontend` — Саша.
- `backend` — Илья. Внутри Илья заводит свои ветки для себя и Дани и сам собирает их в `backend`.
- Ветка `ai` больше не нужна: её код уже в `dev`. Удаляет её Илья, когда перенесёт работу Дани.
- В `dev` сливаются только `frontend` и `backend`, после приёмки.

Перед началом: `git fetch origin && git merge origin/dev` в своей ветке.

Контракт неудобен или непонятен — пишите Саше до того, как делать по-своему. Контракт меняем вместе, а не в одной ветке.

## Формат отчёта

Бэкенд сдаёт один общий отчёт от Ильи, фронт — свой.

```
Ветка и коммит:
Сделано (по пунктам задачи):
Как проверить (команды или шаги):
Не сделано или сделано иначе и почему:
Тесты: что запускал, результат
```

## Бэкенд · Илья (делит с Даней сам)

**Цель раунда:** заявка живёт по машине состояний, клиента можно провести через API от компании до решения. Проверки идут через мок, скоринг и решение считаются по файлу правил. Параллельно готов датасет для модели.

### Конвейер
1. Миграция: таблицы `companies`, `company_members`, `applications`, `application_events`, `check_results`, `scoring_results`, `offers`, `documents`, `feed_items` (поля — `docs/CONVEYOR.md`, раздел 9). Поле `role` у `users`, по умолчанию `client`.
2. Машина состояний одним модулем: таблица разрешённых переходов из `contracts/conveyor.md` («Машина состояний»), проверка роли, запись каждого перехода в `application_events`, оптимистическая блокировка по `version` → `VERSION_CONFLICT`.
3. API клиента из `contracts/conveyor.md`: компании (`/api/registry/{inn}`, `/api/companies`, доверенность), заявки (создать, `PATCH`, `submit`, список, карточка, `withdraw`), документы. Ответы строго по `conveyor.schema.json`, тексты статусов из `dictionaries.json`.
4. Проверка полноты при `submit` → `INCOMPLETE_APPLICATION` и `missing_fields`.
5. Очередь автоматических этапов (можно на базе `generations`): `submitted → checking → scoring → …` с паузами из `rules.checks.stage_delay_seconds`. Заявка не теряется при перезапуске сервера.

### Мок внешних проверок
6. Сервис `integrations-mock/` строго по `contracts/integrations.md`: FastAPI, свой Dockerfile, шесть компаний-сценариев из таблицы, детерминированная генерация по SHA-256 ИНН для остальных, `FAIL_INN`, проверка контрольной суммы ИНН.
7. Клиент к моку в бэкенде по `INTEGRATIONS_URL` с таймаутом 5 с. Ошибка мока → проверка `error` → `manual_review`.

### Скоринг и решение
8. Чистые функции без доступа к БД и сети, только по `contracts/rules/credit_rules.v1.json` (пороги не зашивать в код): стоп-факторы → балльная карта → класс → решение (автоодобрение, встречное предложение, ручное рассмотрение, отказ) → ставка → график платежей. Тексты причин отказа — из `dictionaries.json`.
9. Подключить к конвейеру: после `scoring` заявка уходит в статус по решению; `scoring_results`, `offers`, `decline` заполняются. Встречное предложение: сначала увеличить срок до максимума продукта, потом уменьшить сумму до нагрузки 50% (округление до 10 000 ₽), ниже минимума продукта → `manual_review`.
10. Тесты на каждую строку таблиц раздела 6 `docs/CONVEYOR.md` и на все шесть компаний-сценариев: каждая даёт свой исход из таблицы в `integrations.md`. Платёж и график сверить с примером `contracts/examples/application.approved.json` (1 500 000 ₽, 24 мес., 23,5% → 78 933 ₽).

### Модель (подготовка)
11. **Первым делом лицензии.** Разрешают ли условия GigaChat API использовать ответы для обучения других моделей? Есть ли у GigaChat 3 открытые веса и под какой лицензией? Итог — `ai/LICENSES.md` со ссылками. Если GigaChat API нельзя, генерировать данные открытой моделью.
12. Выбрать базовую модель до ~2 млрд параметров с открытой лицензией (например, Qwen3-1.7B, Apache 2.0). Записать туда же.
13. Генератор датасета `ai/dataset/generate.py` строго по `contracts/ai.md` («Правила для модели и датасета») и `parse-need.schema.json`. Сначала выбирать значения полей, потом просить модель написать текст под них: тогда разметка гарантированно верная. Разнообразие: все цели и сферы из `dictionaries.json`, города из `frontend/src/data/cities.json`, суммы цифрами и словами, сроки словами, опечатки, разговорный стиль, запросы без суммы, без города, не про бизнес.
14. 2–3 тыс. примеров для обучения и отдельно 200+ для отложенной выборки, которая не используется при обучении. Каждый пример проходит схему.
15. `ai/dataset/evaluate.py`: точность по каждому полю для любой функции «текст → ответ». Прогнать на простом базовом решении (регулярки), чтобы было с чем сравнивать модель.

**Готово, когда:**
- через `/docs` можно пройти: привязать компанию `7715881399` → создать заявку на 1 500 000 ₽ / 24 мес. → заполнить → подать → статус сам доходит до `approved` с платежом 78 933 ₽, а в журнале все переходы;
- компании `7755761690` и `776846978815` дают отказ с правильными причинами, `777309114120` — встречное предложение;
- тесты машины состояний: разрешённый переход проходит, запрещённый даёт `INVALID_TRANSITION`, устаревшая версия — `VERSION_CONFLICT`;
- есть записка о лицензиях, датасет, отложенная выборка и вывод `evaluate.py` по базовому решению.

## Фронт · Саша (с Claude)

**Цель раунда:** клиент проходит от компании до поданной заявки на моках фронта по контрактам v2.

1. Моки v2 в `src/api/mock.ts` на примерах из `contracts/examples/`: компании, подбор, заявки со сменой статусов по таймеру.
2. Экран «Компания»: ввод ИНН с проверкой контрольной суммы на лету (та же формула, что `validInn` в `contracts/check.mjs`), карточка из реестра, выбор роли в компании, загрузка доверенности, если роль её требует.
3. Мастер потребности: поле «Опишите своими словами» (`POST /api/needs/parse`, при пустом ответе просто идём дальше) → цель → сумма и срок → залог. Подсветка полей с `confidence < 0.7`.
4. Подбор продукта: карточки «подходит / не подходит, потому что…», платёж, кнопка «Подать заявку» только при `can_apply`.
5. Форма заявки: предзаполнение, финансы за 12 мес., залог для `secured`, согласие на БКИ, автосохранение черновика, список `missing_fields` перед подачей.
6. Экран заявки: таймлайн, блоки «Что сейчас происходит» / «Что нужно от вас» из `status_info`, опрос раз в 2 с в автоматических статусах.
7. Навигация `/app`: Заявки · Новая заявка · Лента · Профиль. Чат убрать из меню, код не удалять. Аналитик после входа уходит на `/bank` (заглушка).

**Готово, когда:** на моках фронта путь «ИНН → потребность → подбор → заявка → подана → статус меняется сам» проходит без ошибок в консоли, `npm test` и `npm run build` зелёные.
