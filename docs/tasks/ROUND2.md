### A. Рабочее место аналитика — главное в раунде
1. Роль `analyst`: все `/api/bank/*` только для неё, для остальных — `NOT_FOUND`. Аналитик не видит черновики.
2. `GET /api/bank/applications?status=a,b` → `bank#/queue_item[]`. Сортировка — дольше всех ждущие сверху. `waiting_minutes` — с последнего перехода. `grade` — из скоринга или `null`.
3. `GET /api/bank/applications/{id}` → `bank#/bank_application`:
   - `checks` — четыре проверки с `summary` для человека, `details` — сырой ответ мока;
   - `scoring` с `factors`, `debt_load_percent`, `rules_version`;
   - `recommendation` системы — и для ручного рассмотрения тоже: что система советует и на каких условиях;
   - `events` — журнал с `actor_name`;
   - `applicant`.
4. `POST /api/bank/applications/{id}/decision` → `bank#/bank_application`. Только из `manual_review`. Проверки и тексты ошибок — как в `mockBank.decide`:
   - сумма и срок в диапазоне продукта, ставка не ниже `rateFrom`;
   - для `counter` изменена сумма или срок, комментарий обязателен;
   - для `decline` нужны причины и комментарий;
   - для `request_info` нужен непустой `info_items`;
   - `VERSION_CONFLICT` по `version`.

   Для будущего ИП добавить условие регистрации ИП в `offer.explanation`. Переход пишется в журнал с `actor = analyst`.
5. `GET /api/bank/stats` → `bank#/stats`: заявки по статусам без черновиков, доля решений системой среди всех решений, среднее время от подачи до решения в минутах.
6. Доступ аналитика к плану заявки (замечание 4).
7. Тесты: доступ по ролям; каждая ветка `decision`, включая ошибки валидации; `VERSION_CONFLICT`; решение вне `manual_review` → `INVALID_TRANSITION`; клиент после решения видит оффер, отказ или запрос данных в своей заявке и в ленте.
