# AI-сервис

FastAPI + GigaChat. Контракт: `contracts/ai.md` (пока в ветке `backend`).

| Метод | Путь | Что делает сейчас |
|---|---|---|
| GET | `/ai/health` | `{"status": "ok"}` |
| POST | `/ai/respond` | GigaChat решает: уточняющие вопросы (3–6), ответ текстом (не по теме, вопрос по плану) или план. Не более 2 раундов вопросов; посторонняя тема возвращается к бизнесу на любом ходе |
| POST | `/ai/summarize` | Мок: склеивает старую память и сообщения пользователя |

Ошибки в формате `{"error": {"code", "message"}}`: 503 `AI_UNAVAILABLE`, 502 `AI_BAD_RESPONSE`, 422 `VALIDATION_ERROR`.

## Запуск локально (Windows, из папки `ai`)

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements.txt
.\.venv\Scripts\python -m uvicorn app.main:app --port 8001 --reload
```

Документация и ручные запросы: http://localhost:8001/docs

Чтобы бэк ходил в этот сервис, а не в моки: в `backend/.env` поставить `MOCK_AI=false`.

## Запуск на сервере

systemd-служба `xronix-ai` на `127.0.0.1:8001` рядом с бэкендом на ВМ, пошагово в [DEPLOY.md](DEPLOY.md). Вариант с Docker: `compose.yaml`.

## Переменные окружения (`.env`)

| Переменная | Что это |
|---|---|
| `GIGACHAT_AUTH_KEY` | Authorization key из кабинета Сбера. Секрет |
| `GIGACHAT_SCOPE` | `GIGACHAT_API_PERS` |
| `GIGACHAT_MODEL` | `GigaChat-2` (быстрее) или `GigaChat-3-Ultra` (лучше тексты, но медленнее, см. таймауты ниже) |
| `GIGACHAT_CA_BUNDLE_FILE` | `certs/russian_bundle.pem`, путь от папки `ai` |
| `AI_DEADLINE_SEC` | Сколько секунд даём на весь ответ, по умолчанию 25 (у бэка таймаут 30). Держать на ~5 с меньше таймаута бэка |
| `GIGACHAT_TIMEOUT_SEC` | Один запрос к GigaChat, по умолчанию 20 |
| `AI_DECIDE_TIMEOUT_SEC` | Шаг «вопросы или план», по умолчанию 8 |
| `AI_MIN_RETRY_SEC` | Повтор плана, только если осталось столько секунд, по умолчанию 10 |

На проде `GigaChat-3-Ultra` (план 19–25 с), бэк ждёт нас 170 с, фронт 180 с: `GIGACHAT_TIMEOUT_SEC=60`, `AI_DEADLINE_SEC=160`, `AI_DECIDE_TIMEOUT_SEC=15`, `AI_MIN_RETRY_SEC=30`. Худший случай: 15 с на вопросы + две попытки плана по 60 с = 135 с, укладываемся с запасом.

## Как устроена генерация плана

1. Промпт (`app/prompts.py`) + JSON-схема плана в `response_format` (`app/plan.py`).
2. Починка кодом (`app/repair.py`): суммы по формулам, нумерация, 12 месяцев, null в кредите.
3. Проверка схемой и правилами `checkPlan`, как у бэка.
4. Не прошло: один повтор, если хватает времени. Потом 502.

Проверка качества на наборе идей: `.\.venv\Scripts\python json_test.py`

## Защита границ роли

`app/prompts.py` фиксирует роль бизнес-консультанта на этапах выбора ответа и генерации плана.
Профиль/теги/память передаются как JSON в пользовательском сообщении, не в системном промпте.
До любых обращений к GigaChat `app/scope.py` применяет локальную политику допуска:

- Смена роли, раскрытие инструкций, поддельные системные сообщения и распознанные посторонние темы получают фиксированный ответ без вызова модели.
- Проверяются Unicode/невидимые символы, смешанные алфавиты, разделённые буквами команды, URL/HTML/Unicode escape и Base64. Декодирование ограничено по объёму и глубине; код не выполняется, ссылки не открываются. Непрозрачные кодированные блоки отклоняются.
- Неопознанная тема также отклоняется: допускаются бизнес-термины и ограниченные формы ответов на текущую структурированную анкету. Приветствия обрабатываются локально.
- При смешении распознанной атаки с бизнес-запросом отклоняется всё сообщение. Обычная смена идеи/бюджета, реклама и слоганы остаются разрешёнными.
- Перед отправкой допустимого запроса удаляются распознанные атаки и посторонние сообщения из истории, небезопасные значения профиля, теги и память. Имя пользователя модели не требуется и не передаётся. Исходные записи пользователя не изменяются.
- В журнал попадают идентификатор сработавшего правила и `model_calls=0`, без исходного текста запроса.

Политика работает и после двух раундов анкеты. Отдельного AI-классификатора для допуска нет.
Системный промпт сохраняется как дополнительный слой для запросов, прошедших фильтр.

**Ограничения:** это строгая лексическая политика, а не универсальное понимание намерений.
Редкие полезные формулировки могут потребовать переформулировки; замаскированный под бизнес
новый вариант атаки может пройти. Нельзя гарантировать нулевую передачу любых мыслимых атак
без полного отказа от свободного текста. Новые сценарии добавляются в регрессионный набор.

Локальные тесты без ключей и вызовов GigaChat (из папки `ai`, зависимости `requirements.txt`):

```sh
python -m unittest discover -s tests -v
```

Набор: 18 тестов; 58 атакующих/посторонних запроса на трёх этапах диалога (LLM-заглушка
падает при любом вызове), 20 допустимых бизнес-запросов, короткие ответы на анкету,
очистка недоверенного контекста, неизменность исходных данных и ограничение больших сообщений истории.

## Теги и текущая идея

`user_context.tags` — теги, вручную сохранённые пользователем в профиле. Допустимые теги
передаются модели, даже если не содержат бизнес-терминов (например, IT или хендмейд).
Модель знает об их наличии и может перечислить по вопросу пользователя. Теги отражают
интересы, но не определяют текущую бизнес-идею и не доказывают прошлых разговоров.
Идея берётся из пользовательских сообщений текущего чата; при отсутствии задаётся открытый вопрос.
Общая междиалоговая `memory` исключается из промптов. Догадки предыдущих ответов ассистента
не считаются подтверждёнными фактами пользователя.

`plan.tags_update` остаётся в схеме для совместимости и относится к результату плана;
backend не переносит его или `summarize.tags` в профиль. Менять теги может только пользователь
через явное редактирование профиля.
