# Датасеты для своей модели: `/ai/consult` и `/ai/parse-need`

Раунд 1: данные, проверка и оценка. Контракт — `contracts/ai.md` (правила для модели и датасета), схемы `contracts/schemas/consult.schema.json` и `parse-need.schema.json`. Лицензии — [`../LICENSES.md`](../LICENSES.md).

**GigaChat не используется:** тексты собираются программно из шаблонов фраз, разметка задаётся до текста. Поэтому датасет воспроизводится без ключей и сети, а разметка верна по построению.

## Команды (из папки `ai`)

```sh
python -m venv .venv                                   # Python 3.12
.venv/Scripts/python -m pip install -r dataset/requirements.txt   # Linux/macOS: .venv/bin/python

python -m dataset.generate                             # оба датасета -> dataset/data/*.jsonl (~3 с, детерминированно)
python -m dataset.validate                             # схема + правила + разбиение; код 1 при ошибке
python -m dataset.evaluate --task consult    --predictor dataset.baseline:consult    --name baseline
python -m dataset.evaluate --task parse_need --predictor dataset.baseline:parse_need --name baseline
python -m unittest tests.test_dataset -v               # проверка, что валидатор ловит ошибки
```

Оценить модель: `--predictor пакет.модуль:функция` (функция `request -> response`) или `--predictions файл.jsonl` со строками `{"id": ..., "response": {...}}`. Результат: `dataset/results/<name>.<task>.json`, в нём метрики, задержка (среднее и p95) и 10 ошибок.

## Размеры

| Датасет | train | holdout | из них в holdout с незнакомыми формулировками |
|---|---|---|---|
| `/ai/consult` | **2828** | **298** | 101 |
| `/ai/parse-need` | **2681** | **296** | 196 |

Holdout при обучении не используется. Как он отделён:
1. **Города.** 20 крупнейших общие, остальные делятся по хешу названия: 150 городов встречаются только в holdout.
2. **Заготовки.** Сначала выбирается смысл примера (сценарий, `state`, факты), и только потом из него пишутся варианты (3 в train, 1 в holdout). Train и holdout строятся из разных заготовок с разными генераторами случайных чисел, поэтому варианты одной заготовки в обе части не попадают.
3. **Формулировки.** Каждая пятая фраза в банках (атаки и смена роли, темы не про бизнес, вопросы про кредит и суммы, редкие бизнесы, фразы цели, формы названий сфер) есть только в holdout. Метрики по таким примерам считаются отдельно (`unseen_phrasing`).
4. **Повторы.** Запросы, совпавшие с holdout дословно, удаляются из train. `validate` проверяет пункты 1–4.

## `/ai/consult`: как устроен пример

```json
{"id": "consult.train.00042", "seed": "consult-train-0013", "scenario": "first_full",
 "rules": ["R2_sphere_code", "R4_one_round", "R5_question_format"],
 "request":  {"history": [], "message": "Хочу открыть кофейню в Казани, есть около 300 тысяч", "state": {...}},
 "response": {"type": "questions", "text": "...", "questions": [...], "state": {...}},
 "meta": {"user_amounts": [300000], "unseen_phrasing": false}}
```

`request` и `response` — ровно то, что ходит по API (каждый проверяется схемой). Остальное — служебное для оценки: `meta.user_amounts` — суммы, которые человек назвал сам (только их модель может вернуть).

Ожидаемый ответ вычисляется по правилам `ai.md` (функция `expected` в `consult.py`):
- `message`, если запрос не про бизнес, это приветствие, попытка сменить роль (в том числе вместе с бизнес-запросом) или вопрос «одобрят ли». `state` не меняется;
- иначе к `state` применяются факты из сообщения. Поправка заменяет старое значение, смена сферы сбрасывает `answers`;
- бизнес не из шаблонов: вопрос «Ближе всего — X. Считаем так?» или выбор из списка; `sphere` остаётся `null`;
- не хватает сферы, города или своих денег — вопросы о недостающем;
- основное стало известно только сейчас — **один** раунд вопросов анкеты шаблона (до 4, ещё не отвеченные);
- основное было известно и до сообщения — `ready`.

В эталонных ответах нет ни одной цифры и ни одного обещания кредита. `own_funds_rub` бывает только из `user_amounts`.

Сценарии: `first_full`, `first_partial`, `first_vague`, `first_all_answers`, `answer_core`, `answer_template`, `ready_direct`, `correction`, `nearest`, `confirm_nearest`, `no_near`, `greeting`, `offtopic`, `role_change`, `mixed_attack`, `credit_promise`, `sums_question`.

## `/ai/parse-need`

Сначала выбираются значения полей, потом текст из кусков: фраза цели (6 целей, с конкретной сферой или про бизнес вообще), город (в трёх формах: «в Казани», «из Казани», «город Казань»), сумма (цифрами, «800к», «1,5 млн», словами, «полтора ляма»), срок («на два года», «18 месяцев», «полгода», «лет на три»), залог («готов заложить квартиру» → `true`, «без залога» → `false`). Добавляются опечатки и разговорный стиль. Отдельно — неоднозначные фразы («Хочу расшириться, нужно миллиона два» → только сумма) и запросы не про бизнес (всё `null`). `confidence` — только для полей не `null`.

## Ограничения

- **Тексты шаблонные.** Разнообразие ограничено банками фраз, поэтому живые формулировки пользователей будут богаче. Высокая точность регулярок по `purpose` (0,96) — признак того, что формулировки цели узнаваемы. Что сделать в раунде 2:
  1. добавить **ручной тестовый набор** на 50–100 настоящих фраз от команды — самая честная проверка;
  2. перефразировать часть train открытой GigaChat 3 Lightning (MIT, локально), сохранив разметку и проверив валидатором.
- **История в consult упрощена:** одна прошлая пара реплик. Как бэкенд будет класть ответы ассистента в `history`, определит Илья во втором раунде. Сейчас там текст и иногда вопросы списком (как в примерах контракта).
- **Правило «одного раунда» по `history` не проверяется:** раунд анкеты считается прошедшим, если основное было известно уже в `state` запроса. Это совпадает с примерами контракта. Если бэкенд будет вести диалог иначе, правило надо уточнить с Ильёй.
- **Бизнес не из шаблонов** оставляет `sphere = null` до подтверждения ближайшей сферы. Контракт этого не запрещает, но и не фиксирует явно.
- **Число вне `min`–`max`** не записывается (бэкенд возьмёт `default`). Обрезать до границы не стали, чтобы не менять сказанное человеком.
- **`confidence`** в разметке parse-need эвристический (по виду записи и опечаткам), точность модели по нему не оценивается.
