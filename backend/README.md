# XRONIX Backend · контракты v1

Рабочий MVP на FastAPI, Python 3.12+, SQLAlchemy и SQLite. Все пути и JSON соответствуют `contracts/api.md` и `contracts/ai.md`. Исходные контракты загружаются из соседней папки `contracts`, без копирования схем в код.

## Запуск одной командой

Из корня репозитория (нужны Python 3.12+ и доступ к PyPI при первом запуске):

```sh
./backend/run.sh
```

Скрипт создаёт `backend/.venv`, устанавливает зависимости, запускает Uvicorn на **0.0.0.0:8000**. База создаётся и обновляется версионными миграциями автоматически. По умолчанию включён `MOCK_AI=true`: сервис Дани не нужен.

Если системный Python ниже 3.12, укажите нужный исполняемый файл при первом запуске: `PYTHON=python3.13 ./backend/run.sh`.

- API: http://localhost:8000/api
- Проверка: http://localhost:8000/health → `{"status":"ok"}`
- Swagger: http://localhost:8000/docs

## Windows: запуск из Git без Docker

Нужны Git и Python 3.12+ с Python Launcher (`py`). В PowerShell:

```powershell
git clone --branch backend --single-branch https://github.com/xrnskew/XRONIX.git
cd XRONIX
.\backend\run.cmd
```

Если репозиторий уже есть, сохранить свои незакоммиченные изменения, затем `git switch backend` и `git pull --ff-only origin backend`. Запускать команды после публикации коммита с исправлением Windows; `git pull` не скачивает локальные неопубликованные изменения Ильи.

`run.cmd` создаёт Windows-окружение `.venv`, ставит requirements и запускает http://localhost:8000 . Без launcher можно создать окружение вручную командой `python -m venv backend\.venv`, затем запустить run.cmd. Виртуальные окружения не переносятся между macOS/Linux и Windows.

На Windows нет обязательного импорта fcntl: используются нативные shared/exclusive блокировки LockFileEx. На Linux/macOS остаётся flock. Блокировки не отключаются. POSIX 0600/0700 и directory fsync относятся к Linux/macOS; в Windows доступ к data/backups регулируют NTFS ACL. Держите локальную копию в личном каталоге пользователя, не в общей доступной папке. Production-процедура Ubuntu не меняется. Фактический запуск на Windows нужно проверить отдельно — текущая среда macOS.

## Переменные окружения

Необязательно скопировать `backend/.env.example` в `backend/.env` и отредактировать. Переменные процесса имеют приоритет над `.env`.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `MOCK_AI` | `true` | `false` включает HTTP-запросы к настоящему ИИ |
| `AI_SERVICE_URL` | `http://localhost:8001` | Базовый URL AI-сервиса, без `/ai` |
| `CORS_ORIGINS` | `http://localhost:5173,http://127.0.0.1:5173` | Разрешённые origin через запятую, без завершающего `/` |
| `JWT_SECRET` | пусто | Для развёртывания задайте случайный секрет от 32 байт |
| `JWT_EXPIRE_MINUTES` | `1440` | Срок действия токена |
| `DATABASE_URL` | абсолютный путь к `backend/data/xronix.db` | SQLite URL, например `sqlite:////srv/backend/data/xronix.db` |
| `CONTRACTS_DIR` | соседняя `contracts/` | Папка с контрактами v1 |

Без `JWT_SECRET` создаётся случайный приватный файл `backend/data/jwt.key` (права 0600). Он сохраняется между перезапусками, поэтому действующие JWT продолжают работать. `backend/data/`, `.env` и виртуальные окружения исключены из Git. Сохраняйте весь каталог `data/`, включая ключ; для резервной копии работающей SQLite используйте SQLite backup API, учитывая WAL.

Для настоящего ИИ:

```sh
MOCK_AI=false AI_SERVICE_URL=http://localhost:8001 ./backend/run.sh
```

Секрет GigaChat здесь не нужен: он остаётся в AI-сервисе.

## Саше: подключение frontend

Существующий frontend-клиент из `origin/frontend` уже поддерживает этот API. В его локальном `.env`:

```dotenv
VITE_USE_MOCKS=false
VITE_API_URL=http://localhost:8000
```

Перезапустить Vite. `VITE_API_URL` **без `/api`** — клиент добавляет префикс самостоятельно. Создать аккаунт в интерфейсе: клиент сохранит JWT и добавит `Authorization: Bearer <token>`.

Сценарий проверки:

1. Зарегистрироваться, при желании заполнить профиль.
2. Создать чат, отправить «Хочу открыть кофейню у метро».
3. Backend вернёт три вопроса из `contracts/examples/reply.questions.json`.
4. Отправить ответы связным `text` и необязательным массивом `answers`.
5. Backend вернёт `type=plan`, свой `plan_id` и сохранённый план. Платёж в примере: 51 878 ₽, нагрузка 35%, вердикт `ok`.
6. Перезагрузить страницу: `GET /api/plans` и `GET /api/plans/{id}` восстановят план. История доступна через `GET /api/chats/{id}`.

Бизнес-план в моковом режиме демонстрационный, из контрактного примера. Его `tags_update` берётся из текущего профиля; моковая память собирается только из сообщений этого пользователя, без данных Александра из примера. Каждый чат независимо проходит вопросы → план; следующие сообщения получают обычную реплику. Прогресс хранится в БД. Новый сценарий начинается в новом чате.

Если frontend открывают на другом компьютере, вместо `localhost` нужен доступный адрес backend; origin frontend нужно добавить в `CORS_ORIGINS`.

## Поведение backend

- Пароли: PBKDF2-HMAC-SHA256, 600 000 итераций, индивидуальная случайная соль; сравнение постоянного времени. JWT: HS256, проверка подписи, срока, issuer и audience.
- Чужие чаты и планы всегда дают `NOT_FOUND`, списки фильтруются по пользователю.
- В ИИ передаются профиль, теги, память, последние 10 сообщений **без текущего**, текущее сообщение только как `text` → `message`. `answers` сохраняется локально и в ИИ не отправляется. Ответы ассистента в контексте включают вопросы/план.
- Все ответы ИИ проверяются исходными JSON Schema draft-07 и смысловыми правилами `check.mjs`. При невалидном результате: первоначальная попытка и до двух повторов. Весь `/ai/respond`, включая повторы, ограничен 30 секундами. Сетевые ошибки/таймауты дают `AI_UNAVAILABLE`, исчерпанные невалидные ответы — `AI_BAD_RESPONSE`.
- Финансовые противоречия, неправильные месяцы/порядок шагов, неполный кредит и слишком маленькая сумма кредита отклоняются до сохранения. После проверки сервер сам пересчитывает funding gap, прибыль, аннуитет, нагрузку и вердикт; проверяет результат снова. Пороги: ≤35% `ok`, ≤50% `risky`, >50% `not_recommended`; прибыль ≤0 означает нагрузку 100%. `recommended_product_id=null` до подключения подбора.
- Сообщение пользователя сохраняется даже при сбое ИИ. Невалидный ответ и план не сохраняются. Точный повтор последнего запроса, который успешно создал план, в течение 120 секунд возвращает тот же ответ и `plan_id`, без нового вызова ИИ и без новых сообщений. Это защита от повторной доставки, а не полная идемпотентность: другие сообщения и повторы после окна обрабатываются заново.
- Лимиты хранятся в SQLite и общие для процессов/рестартов: API — 120 запросов/мин/IP; auth — 20/мин/IP; обращения к ИИ — 6/мин/пользователь и 30/мин на весь backend. Максимум один активный respond на пользователя и четыре на весь backend; создание новых чатов не обходит ограничения. Все значения настраиваются окружением, окна фиксированные по 60 секунд. Ретраи входят в один запрос respond, сводка — отдельный фоновый вызов: это не точный счётчик токенов провайдера. Ответ — `RATE_LIMITED` (429, `Retry-After`). При аварии аренда чата истекает через 120 секунд. Лимиты — защита MVP, не замена облачной защите от DDoS.
- Тело API ограничено 64 KiB, ответ AI — 1 MiB. Некорректные числа NaN/Infinity, Unicode и чрезмерная вложенность JSON отклоняются с контрактной ошибкой. Занятая SQLite возвращает безопасный 429; другие ошибки — INTERNAL, без SQL и параметров.
- Чужой Origin отклоняется до выполнения операции с 400 VALIDATION_ERROR. OPTIONS и все ошибки для разрешённого Origin имеют CORS-заголовки. Отсутствие Origin разрешено для CLI/серверных клиентов; доступ к данным всё равно требует JWT.
- После готового плана `/ai/summarize` обновляет память и добавляет теги без дублей, максимум 12. Это фоновая задача: ответ с планом не ждёт её, сбой не отменяет план и сохраняет прежнюю память. Устаревшая параллельная сводка не перезаписывает более новую память (optimistic compare-and-set). Не является долговечной очередью: при аварийной остановке до завершения сводка может не обновиться.
- Все ошибки API имеют `{ "error": { "code": "…", "message": "…" } }`, сообщения по-русски без технических деталей. Ошибки валидации — 400, а не стандартные FastAPI 422.

## Проверки

```sh
cd backend
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
.venv/bin/python tests/smoke.py
```

Последняя команда выбирает свободный временный порт, не затрагивая уже работающий backend. Она запускает настоящий Uvicorn, выполняет HTTP-сценарий и перезапускает процесс с той же временной SQLite, проверяя JWT, планы, сообщения и моковое состояние. Тестовые данные автоматически удаляются.

Контракты проверяются отдельно из корня:

```sh
cd contracts && npm ci && npm run check
```

## Docker

Сборка **из корня репозитория**, чтобы были доступны оригинальные контракты:

```sh
docker build -f backend/Dockerfile -t xronix-backend .
docker run --rm -p 8000:8000 -e MOCK_AI=true -v xronix-data:/srv/backend/data xronix-backend
```

Для реального AI добавьте `-e MOCK_AI=false -e AI_SERVICE_URL=http://ai:8001` и общую Docker-сеть. Для настройки секретов используйте окружение или `--env-file backend/.env`. Именованный том хранит SQLite и локальный JWT-ключ между контейнерами. Контейнер работает под непривилегированным пользователем.

## Готовность и ограничения

Готовы auth/JWT, профиль, изолированные чаты, сохранение сообщений и планов, моковый диалог, HTTP-интеграция ИИ с валидацией/ретраями/таймаутом, память/теги, финансовые расчёты, CORS, health, автосоздание БД, Dockerfile, тесты.

Результаты фактических проверок записаны в `TEST_RESULTS.md`. Настоящий сервис Дани нужно проверить совместным запуском; тесты HTTP-интеграции используют управляемый `httpx.MockTransport`. Подбор продукта пока возвращает разрешённый `null`. Развёртывание и merge в dev/main выполняются командой отдельно.


## Развёртывание на api.xronix.ru

Готовая конфигурация Backend + Caddy находится в [deploy/README.md](deploy/README.md). Она запускается без AI-сервиса, публикует только 80/443, хранит БД/JWT и сертификаты в постоянных томах, включает healthcheck. Сборка идёт из корня монорепозитория с `contracts/`.

Для frontend на GitHub Pages Саша задаёт Variables `VITE_API_URL=https://api.xronix.ru`, `VITE_USE_MOCKS=false` и пересобирает сайт. Production CORS перечисляет `https://xronix.ru`, `https://www.xronix.ru`, `http://localhost:5173`. DNS/ВМ/сертификат проверяются на реальном сервере.

Дополнительные переменные: `AI_REQUESTS_PER_MINUTE=6`, `AI_GLOBAL_PER_MINUTE=30`, `AI_MAX_CONCURRENT=4`, `API_REQUESTS_PER_MINUTE=120`, `AUTH_REQUESTS_PER_MINUTE=20`. Значения должны быть положительными; wildcard CORS запрещён. JWT-ключ защищён файловой блокировкой при первом параллельном запуске; повреждённый короткий ключ приводит к отказу запуска, а не к небезопасной подписи.

Технические находки, исправления и ограничения аудита перечислены в [AUDIT.md](AUDIT.md). Точное совпадение старой памяти с демонстрационной сводкой Александра исключается при следующем моковом summarize. Остальные старые данные автоматически не удаляются: это могло бы затронуть реальные факты; их следует проверить отдельно.


## Надёжность SQLite и обслуживание

Добавлены SQLite Backup API (включая WAL), проверка целостности копий, суточный запуск и ротация, транзакционные версионные миграции вместо `create_all`, ручное offline-восстановление с подтверждением и безопасный export в смонтированное внешнее POSIX-хранилище. Новых зависимостей/сервисов нет, API и бизнес-логика не менялись.

Из `backend/`: `.venv/bin/python -m app.maintenance backup`, `check`, `verify --backup <файл>`, `migrate`. Команда restore требует точной фразы и остановленного backend; автоматического восстановления нет. HTTP-маршрутов для копий не существует.

Production Compose задаёт `BACKUP_ENABLED=true`, `BACKUP_DIR=/srv/backend/backups`, `BACKUP_RETENTION_COUNT=7`, `BACKUP_TIMEOUT_SECONDS=30`, `DB_MIN_FREE_MB=100`. Локально суточное копирование включается отдельно через `BACKUP_ENABLED=true`. `/health` сохраняет JSON-формат и проверяет реальную таблицу версии/свободное место; полный integrity_check выполняется при backup/check.

Подробная операторская инструкция, ограничения и ручное восстановление: [deploy/DATABASE.md](deploy/DATABASE.md). Снимки БД содержат персональные данные; приватный JWT-ключ резервируется отдельно и не заменяется при restore.
