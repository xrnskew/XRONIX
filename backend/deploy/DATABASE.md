# SQLite: обслуживание на Ubuntu

Команды выполняются из корня XRONIX. Пример сокращения для текущего shell:

```sh
dc() { sudo docker compose --env-file backend/deploy/.env -f backend/deploy/compose.yaml "$@"; }
```

Новых сервисов/зависимостей нет. Используется стандартный Python `sqlite3.Connection.backup()` ([Python](https://docs.python.org/3/library/sqlite3.html#sqlite3.Connection.backup), [SQLite Backup API](https://www.sqlite.org/backup.html)), который читает согласованный снимок, включая committed WAL. Копирование одного живого `xronix.db` через cp/tar не используется.

## Хранение и суточный запуск

- `xronix_backend_data` → `/srv/backend/data`: БД, WAL/SHM, служебная блокировка, отдельный JWT-ключ.
- `xronix_backend_backups` → `/srv/backend/backups`: только проверенные SQLite-снимки и служебная блокировка. Том не подключён к Caddy и не имеет HTTP-маршрута.
- Копии 0600, выделенная папка 0700; контейнер UID 10001. Пример содержит только настройки, не секреты.
- При `BACKUP_ENABLED=true` лёгкая asyncio-задача проверяет необходимость копии раз в минуту; Backup API выполняется в отдельном потоке. Если копий daily нет, первая создаётся при запуске. Следующая — не раньше чем через 24 часа после последней успешной daily-копии. После рестарта отсчёт сохраняется по файлам. Задача не вызывает restore.
- Production Compose включает резервирование по умолчанию; локальный run.sh — только при явном `BACKUP_ENABLED=true`.
- `BACKUP_RETENTION_COUNT=7`: сохраняются **семь последних копий суммарно**, включая ручные, pre-migration и pre-restore. Удаляются только файлы нашего формата, после появления новой проверенной копии. Ошибка копирования не удаляет предыдущие копии. Перед созданием следующей копии очищаются незавершённые `.partial-*` прошлого аварийного запуска.
- SQLite integrity_check, foreign_key_check и известная схема проверяются до публикации снимка. Временный файл, fsync и atomic rename защищают от выдачи недописанной копии за готовую. Готовая копия автономна, без сопутствующего WAL.

В `.env` на сервере:

```dotenv
BACKUP_ENABLED=true
BACKUP_RETENTION_COUNT=7
BACKUP_TIMEOUT_SECONDS=30
DB_MIN_FREE_MB=100
```

Compose задаёт `BACKUP_DIR=/srv/backend/backups`. В обычном локальном запуске можно задать свой **выделенный приватный** каталог; по умолчанию он расположен рядом с БД в `backups/`. Не используйте общий `/tmp` или корень диска. Если каталог существует с открытыми правами, инструмент откажется работать; исправьте владельца/права выделенного каталога, а не общего системного каталога.

30 секунд ограничивают шаги копирования и SQLite-проверки; сбои/зависания самого диска не могут быть надёжно прерваны Python. При увеличении лимита согласуйте Docker stop_grace_period (сейчас 80s, включая завершение HTTP/AI и фоновой копии). При остановке приложение ждёт очистки работающей копии. Внезапное выключение не меняет рабочую БД и не публикует временный снимок.

## Ручная копия и диагностика

```sh
dc exec -T backend python -m app.maintenance backup
dc exec -T backend python -m app.maintenance check
dc exec -T backend python -m app.maintenance verify --backup /srv/backend/backups/ИМЯ_КОПИИ.sqlite3
```

Первая команда печатает имя созданного файла. Подставляйте реальное имя; каталог не отдаётся через API. `check` проверяет целостность/связи, версию схемы и свободное место; `verify` проверяет выбранный снимок без восстановления. CLI-ошибки содержат только код/класс, без SQL, паролей, персональных данных или traceback.

`GET /health` сохраняет прежний формат `{"status":"ok"}`. Теперь он читает реальную таблицу версий и проверяет свободное место data/backup томов. При нехватке места или ошибке БД возвращается существующий 500 INTERNAL; техническая причина остаётся в безопасном логе. Полная проверка содержимого делается при backup/check, а не на каждом публичном health-запросе.

Нужно свободное место для рабочей БД/WAL, семи копий и ещё одной временной копии; резерв `DB_MIN_FREE_MB` не заменяет расчёт размера диска. Старые копии не удаляются заранее, чтобы освободить место для неудачного backup. Следите за ошибками `Database maintenance failed`, возрастом последней daily-копии и заполнением диска. Копия на той же ВМ не защищает от потери ВМ/диска.

## Миграции без удаления данных

`create_all` больше не служит механизмом обновления. Применяются версионные транзакционные миграции из `app/migrations.py`, история в `schema_migrations` содержит номер, имя и SHA-256 определения.

1. Версия 1 принимает существующие users/chats/messages/plans либо создаёт их на пустой БД.
2. Версия 2 добавляет недостающие answers, mock_stage, busy_until и таблицу лимитов. Если поля уже созданы прежним SQLAlchemy, они сохраняются вместе со значениями.
3. Перед миграцией непустой существующей БД обязателен проверенный pre-migration снимок. При ошибке или недостатке места обновление прекращается; DDL откатывается транзакцией. Никаких DROP/пересозданий пользовательских таблиц и перезаписи старых значений.
4. Неизвестная более новая версия, изменённая история или неожиданная схема приводят к отказу запуска, без автоматического исправления/удаления данных.

Перед **первым обновлением** остановите старый backend: предыдущая версия ещё не знает о сервисной файловой блокировке. Для контролируемого обновления:

```sh
dc stop backend
dc build --pull backend
dc run --rm --no-deps backend python -m app.maintenance migrate
dc up -d backend
```

Миграции также проверяются при каждом старте. После обновления они не выполняются повторно. Нуждающееся в миграции приложение откажется запускаться параллельно с уже работающим backend. Блокировки предназначены для одного хоста и локальной POSIX-файловой системы; рабочую SQLite не размещайте на сетевом/object-storage mount.

Для будущего изменения: добавить новую неизменяемую запись MIGRATIONS (SQL-операции или декларативный ADD COLUMN), обновить проверку ожидаемой схемы и ORM, написать тест со старой БД. Уже опубликованные определения/контрольные суммы не редактировать. Изменения с удалением/преобразованием данных требуют отдельной ручной процедуры; текущий механизм их не содержит. Автоматического downgrade нет: откат — только вручную из согласованной копии, с пониманием потери записей после её даты.

## Восстановление: только вручную, после остановки

Сначала проверить снимок, убедиться в его дате, остановить **все** процессы backend, любые SQLite-консоли и внешние писатели. Новая версия держит shared `.service.lock` всю жизнь процесса; restore требует exclusive lock и отказывает при работающем backend. Не удаляйте/не обходите файлы блокировок. Файловый guard не способен остановить стороннюю программу, которая его игнорирует; ответственность за остановку всех SQLite-клиентов остаётся у оператора.

```sh
dc exec -T backend python -m app.maintenance verify --backup /srv/backend/backups/ИМЯ_КОПИИ.sqlite3
dc stop backend
dc run --rm --no-deps backend python -m app.maintenance restore \
  --backup /srv/backend/backups/ИМЯ_КОПИИ.sqlite3 \
  --confirm 'RESTORE /srv/backend/data/xronix.db'
dc up -d backend
curl --fail https://api.xronix.ru/health
```

Без точной фразы `RESTORE <абсолютный путь рабочей БД>` операция запрещена. Это намеренное ручное подтверждение: **никогда не включайте restore в cron, startup или автоматический rollback**.

Порядок внутри restore: проверка источника → отдельный проверенный staged-снимок на том же диске → pre-restore копия текущей БД → безопасный checkpoint и выход из WAL → проверка отсутствия старых sidecar-файлов → атомарная замена рабочей БД. Невалидный/обрезанный/чужой снимок, недоступная safety-копия, активный писатель или недостаток места останавливают операцию до замены. При отказе прежняя рабочая БД сохраняется; иногда режим журнала уже может быть DELETE, при следующем запуске SQLAlchemy снова включает WAL.

Если **сама рабочая БД повреждена**, pre-restore снимок может не пройти проверку. Автоматически обходить это запрещено. Остановите всё, вручную сохраните весь повреждённый набор db/WAL/SHM/служебных файлов в отдельный закрытый карантин вне репозитория, освободите исходное имя БД и sidecar-файлы, затем повторите подтверждённое restore. Не удаляйте WAL отдельно от повреждённой БД. При отказе checkpoint из-за неизвестных клиентов не стирайте WAL — найдите/остановите клиентов.

Снимок БД **не содержит JWT-ключа**. Restore не заменяет существующий ключ. Храните `data/jwt.key` или заданный JWT_SECRET отдельно в защищённой резервной копии/хранилище секретов; без него прежние JWT станут недействительными. Ключ и `.env` никогда не отправлять в Git/чат. Пользователи и изменения, созданные после даты выбранной копии, при восстановлении будут утрачены — это ожидаемый откат данных, который подтверждает оператор. После восстановления проверить вход, профиль, историю чата и сохранённый план.

## Внешнее хранилище без SDK/платных подключений

Есть только ручной `export`: передача выбранной готовой копии в уже смонтированный **приватный POSIX-каталог**. Проверяются SQLite, SHA-256 исходника/результата, права, fsync; существующий файл не перезаписывается. Нужна поддержка atomic hard link на принимающей файловой системе. Рабочая БД туда не монтируется.

Пример после самостоятельной настройки внешнего зашифрованного/защищённого диска или сетевого POSIX-хранилища на `/mnt/xronix-offsite`:

```sh
dc run --rm --no-deps -v /mnt/xronix-offsite:/srv/offsite backend \
  python -m app.maintenance export \
  --backup /srv/backend/backups/ИМЯ_КОПИИ.sqlite3 \
  --destination /srv/offsite/xronix
```

До запуска проверьте фактическое монтирование: обычный каталог с таким именем ещё не является внешним хранилищем. Внешнему хранилищу нужна отдельная политика удержания/доступа; локальная ротация его не удаляет. Снимки содержат почты, хеши паролей, переписку и планы — передача только по защищённому каналу, хранение с шифрованием и ограничением доступа. Сам export шифрование не выполняет. Object Storage можно подключить позже отдельным операторским upload готового проверенного файла; сейчас ни бакет, ни облачные ключи, ни платный сервис не создаются и не используются.

Каталоги backups/backup-export и SQLite-файлы исключены из Git/build context, Dockerfile копирует только код app и requirements. Резервные копии создаются после запуска в томе, а не внутри публичного образа.
